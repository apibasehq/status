Emergency merge procedure

Use this page when a change can't wait for Apibase:

  • Apibase can't publish the `Apibase Gate` result at all, for example during a total outage or while the outbound connector to your private Git server is down.
  • Apibase can't analyze changes and your organization holds merges until it's back (the `strict` policy): the check reads «On hold until Apibase is back».

If your organization uses the continuity policy, Apibase passes the check without analysis while it can't analyze changes, and you don't need this procedure. Every merge made without an Apibase analysis is recorded and analyzed when Apibase is back. It is never shown as an approval.

GitHub with an emergency bypass team

When merge enforcement was activated, your organization chose a team that the Apibase ruleset lists as a bypass actor in pull-request-only mode. A member of that team can merge one pull request whose `Apibase Gate` check is missing or pending.

  1. Open the pull request and confirm that the only failing requirement is `Apibase Gate`.
  2. Select the option to merge without waiting for requirements to be met (bypass rules).
  3. Write the incident and the reason in the pull request, so reviewers can find it later.
  4. Merge. GitHub records the bypass, and Apibase detects it and analyzes the change when it's back.

The team can bypass the rule at any time, not only during incidents. Keep it small, and review its use in Apibase under ungated merges and bypass events.

GitHub without an emergency bypass team

Only a repository administrator can proceed.

  1. Open the repository settings, then Rules, then Rulesets, and select the Apibase ruleset.
  2. Set its enforcement status to Disabled and save. This lifts the Apibase requirement for every pull request on the protected branches, so keep the window short.
  3. Merge the pull requests that cannot wait.
  4. Set the ruleset back to Active. Apibase also repairs drift in its ruleset when it recovers.

GitLab

External status checks only accept a passed, failed or pending response, so GitLab has no designated emergency actor. There are two exits, both broader than a GitHub bypass team.

  • Post a passed response for the exact head of one merge request, as a user allowed to approve it (Developer role or higher). Find the check id with `GET /projects/:id/external_status_checks`.
  • A Maintainer or Owner can clear the project setting Status checks must succeed in Settings, Merge requests. This lifts every external status check of the project; restore it afterwards.
curl --request POST --header "PRIVATE-TOKEN: <token>" \
  "https://gitlab.example.com/api/v4/projects/<project-id>/merge_requests/<iid>/status_check_responses" \
  --data "sha=<head-sha>&external_status_check_id=<check-id>&status=passed"

GitLab rejects a response for a commit that is not the current head of the merge request. If the project requires all threads to be resolved, also resolve the Apibase "API review" thread of the merge request; Apibase resolves it by itself when the change passes once it's back.

After Apibase recovers

Apibase redelivers the GitHub webhooks that failed, re-enables GitLab hooks disabled by failed deliveries, checks open pull and merge requests again, and analyzes what merged during the incident. Organization administrators are notified when that analysis is ready.
